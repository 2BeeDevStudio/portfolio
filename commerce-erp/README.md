# 커머스 통합관리 ERP (유지보수 · 기능개선)

여러 오픈마켓의 **주문·출고·정산·CS·마진**을 한곳에서 관리하는 사내 ERP입니다. 백엔드 컨트롤러 50여 개 규모의 **운영 중인 대형 시스템**에서, 실사용 중 발생하는 지표 오류·버그를 고치고 신규 기능을 추가하는 **유지보수 및 기능 개선**을 담당했습니다.

---

## 기술 스택

| 구분      | 기술                                                       |
| --------- | ---------------------------------------------------------- |
| Backend   | Node.js, Express (MVC — routes / controllers / models)     |
| Database  | MariaDB / MySQL (원시 SQL 기반, 영업일·공휴일 로직 포함)    |
| Frontend  | React, Material-UI (관리자 대시보드)                       |
| 도메인    | 주문·운송장(출고), 정산, CS/클레임, 마진, 단가, 상품관리   |

---

## 담당 범위

운영 중인 시스템이라 **회귀(regression) 없이** 고치는 것이 핵심이었습니다. 주요 작업을 세 차례에 걸쳐 진행했습니다.

| 구분 | 작업 항목 |
| --- | --- |
| **지표/버그** | 운송장 출고율 계산 기준 정정, 필터 상태 전체선택 버그, 멀티조회 시 조회 풀림 버그, 상품관리 엑셀 전체 다운로드 오류 |
| **기능 추가** | 상세내역 페이징, 일괄메모 이어쓰기, 상품별 마진확인(신규 메뉴), 판매중/종료 불일치 검색, 판매량 조회(일·주·월) |
| **성능** | 상품 수정 시 품절 처리 속도 개선, 상품관리(단가) 후기 필터 성능 개선 |
| **UX** | 쇼핑몰 URL 하이퍼링크, CS 엑셀 다운로드 시 차감금액 표출, 단가 변경 시 품절 관련 에러 메시지 정리 |

## 대표 작업 상세

### 1. 출고율(배송완료율) 지표 정확도 개선 — "D-2 기준"

**문제:** 운송장 조회 화면의 출고율이 현장 체감과 **불일치**하게 낮게 표시됨. 관리자가 배송 성과를 잘못 판단할 수 있는 지표 신뢰도 문제.

**원인 분석:** 출고율을 `배송완료 건 / 전체 출고 건` 으로 계산하면서, **오늘(D)·어제(D-1)에 막 출고된 건까지 분모에 포함**하고 있었음. 이제 막 출고한 건은 물리적으로 배송이 완료될 시간 자체가 없어, 이 건들이 분모를 부풀려 출고율을 실제보다 낮게 왜곡함.

**해결:** 배송이 완료될 물리적 시간이 확보된 **전전날(D-2)까지 출고분만** 분모·분자 대상으로 삼도록 계산 기준을 정정.

```sql
-- todayShippingRate: 전전날(D-2)까지 출고분 대비 배송완료율
ROUND(
  100 * SUM(
    CASE
      WHEN delivery_status IN ('배송완료', '배달완료')
        AND DATE(invoice_date) <= DATE_SUB(CURDATE(), INTERVAL 2 DAY)   -- D-2까지만 분자
      THEN 1 ELSE 0 END
  ) /
  NULLIF(
    SUM(
      CASE
        WHEN DATE(invoice_date) <= DATE_SUB(CURDATE(), INTERVAL 2 DAY)  -- D-2까지만 분모
        THEN 1 ELSE 0 END
    ), 0   -- 0으로 나누기 방지
  ), 2
) AS todayShippingRate
```

**결과:** 출고율이 현장 실제와 일치. 지표가 "오늘 막 넣은 주문 때문에 낮아 보이는" 착시가 사라져 관리자가 신뢰하고 볼 수 있는 수치가 됨.

> 이 화면의 출고 도메인은 단순 카운트가 아니라, **영업일·공휴일을 반영한 "장기 미출고" 판정**(결제일 + 3영업일, 주말·`tb_holidays` 공휴일 제외)까지 포함하는 복잡한 로직이었습니다. 도메인 규칙을 정확히 이해한 뒤 손대야 회귀를 피할 수 있었습니다.

---

### 2. 일괄 메모 — "이어쓰기" + 필터 상태 전체선택 버그

두 가지를 함께 개선했습니다.

**기능 추가 — 이어쓰기:** 기존 일괄 메모는 여러 건에 메모를 입력하면 **기존 내용을 덮어쓰기**만 가능했음. 기존 메모를 살리고 뒤에 덧붙이는 **이어쓰기** 모드를 추가해, 이력을 누적할 수 있게 함.

**버그 수정 — 필터 상태 전체선택:** 목록을 필터링한 상태에서 '전체선택'을 누르면 **화면에 보이지 않는 전체 데이터까지 선택**되어 의도치 않은 대상에 일괄 작업이 적용되던 문제. '전체선택'의 범위를 **현재 필터가 적용된 결과로 한정**하도록 수정. (데이터 손상으로 이어질 수 있던 위험한 버그)

---

### 3. 대용량 상세내역 — 페이징 도입

**문제:** 상세내역을 한 번에 전부 렌더링해 데이터가 많을수록 응답·화면이 느려짐.

**해결:** 상세내역에 **50개 단위 페이징**을 도입해 초기 로딩량과 렌더링 부담을 줄임. 대량 데이터에서도 일정한 응답성을 확보.

---

### 4. 성능 — 상품 수정 시 품절 처리 속도 개선

상품 정보를 수정할 때 연동되는 **품절 처리 로직이 느려** 저장 체감이 나빴던 문제를, 쿼리/처리 흐름을 다듬어 개선. 더불어 단가 변경 시 품절 관련 에러 메시지가 부정확하게 노출되던 부분도 정리.

---

### 5. 신규 기능 — 상품별 마진 확인 / 판매상태 보고서

- **상품별 마진 확인 (신규 메뉴)** — 마켓별 마진·거래처별 단가를 익스펜더로 펼쳐보는 마진 분석 화면 추가.
- **판매중/종료 불일치 검색** — 마켓과 시스템 간 판매 상태가 어긋난 상품을 찾아내는 검색 기능.
- **판매량 조회 (일·주·월)** — 기간 단위 판매량 집계 + 자동 관리상품명 지정.

---

## 회고

제일 기억에 남는 건 출고율 지표를 고친 일이었습니다. 처음엔 계산식이 틀린 줄 알고 쿼리만 들여다봤는데, 식은 맞고 "오늘 막 출고한 건은 아직 배송이 끝날 수가 없다"는 업무 현실이 빠져 있던 게 원인이었습니다. 코드가 아니라 업무 흐름을 이해하고 나서야 D-2 기준이 답이라는 게 보였습니다.

내가 처음부터 짠 시스템이 아니라 컨트롤러만 50개가 넘다 보니, 처음엔 어디를 고쳐야 할지 찾는 데 시간이 더 걸렸습니다. 운영 중인 시스템이라 "기존 동작을 안 깨는 것"을 최우선에 뒀고, 특히 필터가 걸린 상태에서 전체선택이 전체 데이터에 적용되던 버그처럼 데이터가 잘못 바뀔 수 있는 부분부터 막았습니다.
