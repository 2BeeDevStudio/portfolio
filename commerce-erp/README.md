# 커머스 통합관리 ERP (유지보수 · 기능 개선)

> 유지보수 · 기능 개선 · 2025.09 ~ 2026.04

여러 오픈마켓의 주문, 출고, 정산, CS, 마진을 한곳에서 관리하는 사내 ERP입니다. 백엔드 컨트롤러가 50개가 넘는, 이미 운영 중인 큰 시스템에서 실제로 쓰다가 생긴 지표 오류와 버그를 고치고 새 기능을 더하는 일을 맡았습니다.

## 대표 작업

### 1. 출고율이 실제보다 낮게 나오던 문제 (D-2 기준)

운송장 조회 화면의 출고율이 현장에서 느끼는 것보다 낮게 나왔습니다. 관리자가 배송 성과를 잘못 판단할 수 있는 문제였습니다.

출고율을 `배송완료 건 / 전체 출고 건`으로 계산하면서, 오늘과 어제 막 출고된 건까지 분모에 넣고 있었습니다. 방금 출고한 건은 아직 배송이 끝날 수 없는데 분모만 키워서 출고율을 낮췄습니다.

배송이 끝날 시간이 충분히 지난 전전날(D-2)까지 출고된 건만 분모와 분자에 넣도록 계산 기준을 바꿨습니다.

```sql
-- todayShippingRate: 전전날(D-2)까지 출고된 건 대비 배송완료 비율
ROUND(
  100 * SUM(
    CASE
      WHEN delivery_status IN ('배송완료', '배달완료')
        AND DATE(invoice_date) <= DATE_SUB(CURDATE(), INTERVAL 2 DAY)   -- 분자도 D-2까지
      THEN 1 ELSE 0 END
  ) /
  NULLIF(
    SUM(
      CASE
        WHEN DATE(invoice_date) <= DATE_SUB(CURDATE(), INTERVAL 2 DAY)  -- 분모도 D-2까지
        THEN 1 ELSE 0 END
    ), 0   -- 0으로 나누지 않게
  ), 2
) AS todayShippingRate
```

바꾼 뒤에는 출고율이 현장과 맞게 나왔고, 오늘 들어온 주문 때문에 낮아 보이는 일이 없어졌습니다.

이 화면은 단순히 건수를 세는 곳이 아니라, 결제일로부터 3영업일(주말과 공휴일 테이블 제외)이 지나도 출고되지 않은 건을 "장기 미출고"로 판정하는 로직까지 들어 있었습니다. 업무 규칙을 먼저 정확히 이해한 뒤에 손을 대야 다른 계산을 깨지 않을 수 있었습니다.

### 2. 일괄 메모 이어쓰기와 필터 상태 전체 선택 버그

두 가지를 함께 고쳤습니다.

기존 일괄 메모는 여러 건에 메모를 넣으면 원래 내용을 덮어쓰기만 했습니다. 원래 메모 뒤에 덧붙이는 이어쓰기를 더해 이력이 남도록 했습니다.

목록을 필터링한 상태에서 전체 선택을 누르면 화면에 보이지 않는 데이터까지 선택돼, 의도하지 않은 건에 일괄 작업이 적용되는 버그도 있었습니다. 전체 선택이 지금 필터가 걸린 결과에만 적용되도록 고쳤습니다. 데이터가 잘못 바뀔 수 있는 버그라 가장 먼저 처리했습니다.

### 3. 상세내역 페이징

상세내역을 한 번에 다 그려서 데이터가 많을수록 화면이 느려졌습니다. 50개씩 나눠 보여 주도록 바꿔 처음 불러오는 양을 줄였고, 데이터가 많아도 화면이 일정하게 반응하게 했습니다.

### 4. 상품 수정 시 품절 처리 속도

상품 정보를 저장할 때 함께 도는 품절 처리가 느려 저장이 오래 걸렸습니다. 쿼리와 처리 순서를 다듬어 빨라지게 했고, 단가를 바꿀 때 품절 관련 오류 메시지가 엉뚱하게 나오던 것도 정리했습니다.

### 5. 새 기능

- 상품별 마진 확인(새 메뉴): 마켓별 마진과 거래처별 단가를 펼쳐 볼 수 있는 화면을 만들었습니다.
- 판매중·종료 불일치 검색: 마켓과 시스템의 판매 상태가 서로 다른 상품을 찾아 줍니다.
- 판매량 조회(일·주·월): 기간별로 판매량을 모아 보고, 관리 상품명을 자동으로 붙입니다.

## 회고

가장 기억에 남는 건 출고율을 고친 일입니다. 처음에는 계산식이 틀린 줄 알고 쿼리만 들여다봤는데, 식은 맞았고 "오늘 막 출고한 건은 아직 배송이 끝날 수 없다"는 업무 현실이 빠져 있었습니다. 코드보다 업무 흐름을 이해하고 나서야 D-2 기준이 답이라는 게 보였습니다.

처음부터 내가 짠 시스템이 아니고 컨트롤러만 50개가 넘다 보니, 처음에는 어디를 고쳐야 하는지 찾는 데 시간이 더 걸렸습니다. 운영 중인 시스템이라 기존 동작을 깨지 않는 걸 가장 먼저 생각했고, 필터가 걸린 상태에서 전체 선택이 전체 데이터에 적용되던 버그처럼 데이터가 잘못 바뀔 수 있는 부분부터 막았습니다.
